## Was der Client braucht

- seinen eigenen privaten Schlüssel (nur auf dem Client);
- den öffentlichen Schlüssel des Servers;
- den Server-Endpoint (IP/Domain + UDP-Port);
- die Tunneladresse des Clients;
- `AllowedIPs`: welche Ziele durch den Tunnel gehen;
- optional DNS, PersistentKeepalive.

Die Server-Einrichtung steht in 021; der Client braucht nie den privaten Schlüssel des Servers.

## Beispiel für Linux `wg-quick`

```ini
[Interface]
PrivateKey = <client-private-key>
Address = 10.10.0.2/24
# DNS = 10.10.0.1

[Peer]
PublicKey = <server-public-key>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.10.0.0/24
PersistentKeepalive = 25
```

Im Echtbetrieb:

```sh
sudo install -m 600 client.conf /etc/wireguard/wg0.conf
sudo wg-quick up wg0
sudo wg show
```

`Endpoint` verwendet eine öffentliche Adresse bzw. Domain; dieses Labor nutzte die LAN-Adresse `192.168.1.2:51820`.

## Hier verwendete minimale manuelle Konfiguration

Erstellen Sie im PVE-netns die Schnittstelle mit `ip` + `wg`:

```sh
ip link add wg0 type wireguard
wg set wg0 private-key /tmp/wg-client.key \
  peer <server-public-key> \
  endpoint 192.168.1.2:51820 \
  allowed-ips 10.10.0.0/24 \
  persistent-keepalive 5
ip addr add 10.10.0.2/24 dev wg0
ip link set wg0 up
```

Der Client `192.168.1.251/24` erreichte das Labor-LAN über veth; `wg0` transportierte nur `10.10.0.0/24`.

## AllowedIPs wählen

| Ziel | AllowedIPs | Zusätzlich nötig |
|---|---|---|
| nur Tunnel-IPs | `10.10.0.0/24` | Server-Peer erlaubt die Tunnel-IP des Clients |
| LAN des Servers | `10.10.0.0/24, 192.168.1.0/24` | Server-Forwarding/Rückroute oder NAT; Firewall-Forward |
| Full-Tunnel/Heimnetz | `0.0.0.0/0, ::/0` | Server-NAT/Forward, DNS, mögliche Kill-Switch-Konflikte |
| ein LAN-Host | `10.10.0.0/24, 192.168.1.10/32` | minimale Exposition; Server-Route weiterhin nötig |

Enthält `AllowedIPs` die Endpoint-IP (z. B. `0.0.0.0/0`), fügt `wg-quick` eine Ausnahmeroute für den Endpoint hinzu; bei manueller Konfiguration müssen Sie den Endpoint selbst aus dem Tunnel heraushalten, sonst läuft der Handshake in einer Schleife in `wg0`.

## Prüfen

```sh
wg show
ip addr show wg0
ip route
ping -c 3 10.10.0.1
curl -sSI --max-time 5 http://10.10.0.1/ | head -3
```

In diesem Labor:

- Handshake vor 3 Sekunden;
- `transfer 124 B received, 180 B sent`;
- Tunnel-Ping 4/4;
- HTTP 200 (LuCI des Servers).

## DNS

- `DNS = 10.10.0.1` weist den Client nur auf die Tunneladresse hin; der Server muss DNS tatsächlich abhören/weiterleiten;
- bei `AllowedIPs=0.0.0.0/0` sind DNS-Leaks/Kill-Switch eine weitere Ebene;
- dieses Labor verlegte DNS nicht in den Tunnel; `nslookup`-Ergebnisse beweisen kein DNS durch den Tunnel.

## Windows / Smartphone

- Prüfen Sie beim Import `AllowedIPs`, Endpoint und DNS;
- Smartphones nutzen standardmäßig oft „Always-on/VPN bei Bedarf“; testen Sie zuerst Trennen und Wiederverbinden;
- kopieren Sie private Schlüssel nie aus Chats oder Screenshots;
- dieses Labor testete weder Windows noch Android noch iOS; behaupten Sie nicht „alle Plattformen verifiziert“.

## Häufige Fehler

### Kein Handshake

- öffentlicher Server-Schlüssel und privater Client-Schlüssel passen nicht zusammen;
- Endpoint/Port/Firewall;
- `allowed_ips` des Server-Peers enthält die Tunnel-IP des Clients nicht;
- die Uhrzeit spielt für WireGuard keine Rolle, die Schlüssel aber schon.

### Ping auf die Tunnel-IP schlägt fehl

- die Schnittstelle hat keine Adresse bzw. ist down;
- `allowed_ips` enthält `10.10.0.0/24` nicht;
- Firewall-Zone des Servers;
- die Endpoint-Route wurde fälschlich in den Tunnel geleitet.

### Tunnel antwortet, LAN nicht erreichbar

- `AllowedIPs` enthält das LAN-Präfix nicht;
- der Server hat kein Forwarding/keine Rückroute/kein NAT;
- Firewall-Forward des Servers;
- setzen Sie Tunnel-Konnektivität nicht mit LAN-Konnektivität gleich.

### DNS funktioniert nicht

- am Client ist kein DNS gesetzt;
- der Server-DNS lauscht nicht auf der Tunneladresse;
- Full-Tunnel-Route/DNS-Leak;
- testen Sie IP, Namen und DNS-Server getrennt, bevor Sie die Konfiguration ändern.
