## What the client needs

- its own private key (client only);
- server public key;
- server endpoint (IP/domain + UDP port);
- client tunnel address;
- `AllowedIPs`: which destinations go through the tunnel;
- optional DNS, PersistentKeepalive.

Server setup is in 021; the client never needs the server private key.

## Linux `wg-quick` example

```ini
[Interface]
PrivateKey = <client-private-key>
Address = 10.10.0.2/24
# DNS = 10.10.0.1

[Peer]
PublicKey = <server-public-key>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.10.0.0/24
PersistentKeepalive = 25
```

Real use:

```sh
sudo install -m 600 client.conf /etc/wireguard/wg0.conf
sudo wg-quick up wg0
sudo wg show
```

`Endpoint` uses a public address/domain; this lab used the LAN address `192.168.1.2:51820`.

## Minimal manual config used here

In the PVE netns, create the interface with `ip` + `wg`:

```sh
ip link add wg0 type wireguard
wg set wg0 private-key /tmp/wg-client.key \
  peer <server-public-key> \
  endpoint 192.168.1.2:51820 \
  allowed-ips 10.10.0.0/24 \
  persistent-keepalive 5
ip addr add 10.10.0.2/24 dev wg0
ip link set wg0 up
```

Client `192.168.1.251/24` reached the lab LAN via veth; `wg0` carried only `10.10.0.0/24`.

## Choosing AllowedIPs

| Goal | AllowedIPs | Also needs |
|---|---|---|
| tunnel IPs only | `10.10.0.0/24` | server peer allows the client tunnel IP |
| server LAN | `10.10.0.0/24, 192.168.1.0/24` | server forward/return route or NAT; firewall forward |
| full tunnel/home | `0.0.0.0/0, ::/0` | server NAT/forward, DNS, possible kill-switch conflicts |
| one LAN host | `10.10.0.0/24, 192.168.1.10/32` | minimal exposure; server route still needed |

If `AllowedIPs` includes the Endpoint IP (e.g. `0.0.0.0/0`), `wg-quick` adds an exception route for the Endpoint; with manual config you must keep the Endpoint out of the tunnel or the handshake loops into `wg0`.

## DNS

- `DNS = 10.10.0.1` only points the client at the tunnel address; the server must actually listen/forward DNS;
- with `AllowedIPs=0.0.0.0/0`, DNS leaks/kill switch are another layer;
- this lab did not move DNS into the tunnel; `nslookup` results do not prove DNS through tunnel.

## Windows / phone

- On import, verify `AllowedIPs`, Endpoint and DNS;
- phones may default to “always-on/VPN on demand”; test disconnect/reconnect first;
- never copy private keys from chat/screenshots;
- this lab did not test Windows/Android/iOS; do not claim “all platforms verified”.

## Common failures

### No handshake

- server public/client private key mismatch;
- endpoint/port/firewall;
- server peer `allowed_ips` lacks the client tunnel IP;
- clock does not matter for WireGuard, but keys do.

### Tunnel IP ping fails

- interface has no address/is down;
- `allowed_ips` lacks `10.10.0.0/24`;
- server firewall zone;
- endpoint route incorrectly sent into the tunnel.

### Tunnel pings, LAN unreachable

- `AllowedIPs` lacks the LAN prefix;
- server has no forward/return/NAT;
- server firewall forward;
- do not equate tunnel connectivity with LAN connectivity.

### DNS does not work

- client has no DNS set;
- server DNS is not listening on the tunnel address;
- full-tunnel route/DNS leak;
- test IP, name and DNS server separately before changing config.
